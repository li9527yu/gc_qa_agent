# Easy-RAG 项目 Agent 化能力评估报告

> **评估日期**：2026-04-03  
> **评估视角**：从 Agent 架构与工程化角度  
> **评估范围**：后端核心服务（`app/`）、前端界面（`front/`）、文档体系（`docs/`）

---

## 一、项目定位与现状概述

Easy-RAG 当前是一个面向**工程造价领域**的智能问答系统，核心能力包括：

1. **知识问答（RAG）**：基于上传文档进行 BM25 + 向量混合检索，流式生成回答
2. **价格推荐**：对接信息价/厂商报价/智诚信息价三个渠道，进行数据查询与统计分析
3. **意图识别**：通过 LLM 判断用户问题是知识问答还是价格查询
4. **对话管理**：渐进式实体补全（收集材料名称、省份、城市等字段）
5. **文件管理**：支持 PDF/TXT/MD 上传，自动重建向量库

**当前技术栈**：FastAPI + Milvus + BGE 嵌入模型 + DeepSeek/本地 LLM + Streamlit 前端

---

## 二、核心结论

从 Agent 项目的标准来看，Easy-RAG 目前处于 **"功能系统" 阶段**，尚未达到 **"Agent 系统"** 的要求。

- **如果是 RAG + 价格查询工具**：当前架构基本可用，工程化有一定基础（双缓冲重建、缓存机制、流式响应）
- **如果是 AI Agent**：在**规划推理、工具抽象、记忆系统、自我修正**等核心维度存在明显短板，需要较大重构

---

## 三、不足之处详细分析

### 3.1 缺少真正的 Agent 推理与规划循环

#### 现状
系统的决策是**硬编码的 if-else 路由**：

```
用户输入 → 意图识别（knowledge_qa / price_recommendation / other）
         → 知识问答走 /api/v1/query/stream
         → 价格查询走 /api/v1/query/price
```

这本质上是**分类器 + 两个独立服务拼接**，不是 Agent 的"观察-思考-行动"循环。

#### 缺失的能力
| 能力 | 说明 |
|------|------|
| **任务拆解** | 无法将复杂问题拆分为多步执行（如"先查规范定义，再匹配材料，最后查价格"） |
| **动态规划** | 执行过程中无法根据中间结果调整下一步策略 |
| **观察-行动循环（ReAct）** | 没有 Observation → Thought → Action 的迭代过程 |
| **条件分支** | 无法处理"如果 A 查不到，尝试 B"这类动态分支逻辑 |

---

### 3.2 工具调用（Tool Calling）过于原始

#### 现状
- 价格查询 API 是唯一接近"工具"的模块，但**完全硬编码在 `rag_service.py` 中**
- 使用同步函数调用（`_get_infor_material`、`_get_factory_material`），没有统一的 Tool Schema
- 添加新工具需要侵入式修改 `RAGService` 和 `endpoints.py`

#### 问题
```python
# 当前方式：硬编码分支
if channel == "information_price":
    result = self._get_infor_material(entities)
elif channel == "manufacturer_price":
    result = self._get_factory_material(entities)
```

这不是标准 Tool Calling，无法：
- **组合多个工具**：先 RAG 查规范，再 Price API 查价格
- **让 LLM 自主选择工具**：系统替 LLM 做了所有决策
- **动态注册新工具**：每加一个工具都要改核心业务代码
- **获取工具执行的元信息**：执行了什么、参数是什么、结果如何

---

### 3.3 缺乏反思与自我修正（Reflection / Self-Correction）

#### 现状
- 实体抽取失败时，直接返回空字典或错误信息
- 价格 API 返回空结果时，仅提示"查询条件没有符合的样本"
- 没有基于执行结果的 Retry 或条件放宽策略

#### 应有的行为（Agent 标准）
```
1. 用户查询"深圳钢筋价格"
2. 实体抽取得到 {materialName: "钢筋", city: "深圳市"}
3. 调用价格 API → 返回 0 条
4. 【反思】可能是"钢筋"太宽泛，尝试匹配"螺纹钢"、"HRB400"
5. 【修正】扩大查询范围或向用户确认具体规格
6. 最终给出有用回答或精准追问
```

---

### 3.4 对话历史存在严重并发与状态隐患

#### 现状
```python
# app/api/endpoints.py 第 81 行
messages: list[dict] = []
```

这是一个**全局共享的 Python 列表**，所有并发请求共用同一组对话历史。

#### 风险
| 风险 | 场景 |
|------|------|
| **会话串扰** | 用户 A 的上下文混入用户 B 的查询 |
| **状态丢失** | 多实例部署时，每个实例的 `messages` 互不相通 |
| **内存泄漏** | 长期运行后 `messages` 只增不减（虽然有截断，但截断逻辑不精确） |
| **无法扩展** | 无法支持用户登录、多会话管理、历史会话回溯 |

---

### 3.5 对话管理器本质是"表单收集器"，非 Agent Memory

#### 现状
`DialogueManager` 的核心逻辑是**槽位填充（Slot Filling）**：
- 必填：`materialName`
- 选填：`province` → `city` → `materialModelSpec` → `brand`

#### 问题
- 只能处理**价格查询**这一种线性收集流程
- 无法支持多轮推理中的**中间变量记忆**（如"刚才查到的均价是 25 元"）
- 没有**长期记忆**（用户偏好、常用材料、历史行为模式）
- 没有**跨会话记忆**（用户上周问过的问题，本周无法关联）

---

### 3.6 RAG 子系统缺少 Agentic RAG 关键环节

#### 现状
RAG 流程：BM25 → 向量检索 → 去重 → 重排序 → LLM 生成

这是一个**单次检索、单次生成**的管道。

#### 缺失的 Agentic RAG 能力
| 能力 | 现状 | 期望 |
|------|------|------|
| **查询重写** | ❌ 没有 | 将"这个多少钱"结合上下文重写为具体查询 |
| **检索路由** | ❌ 没有 | 根据问题类型选择法规库 / 规范库 / 案例库 |
| **多跳检索** | ❌ 没有 | 先查规范名称，再查该规范对某材料的具体要求 |
| **检索结果验证** | ❌ 没有 | 判断检索到的文档是否足够回答问题 |
| **Self-RAG** | ❌ 没有 | 如果文档不足，主动补充检索或拒绝回答 |

---

### 3.7 没有评估与反馈闭环

#### 现状
- 没有检索准确率的监控指标（如 Recall@K、MRR、NDCG）
- 没有答案质量的自动化评估（Faithfulness、Answer Relevance、Hallucination Rate）
- 没有用户反馈收集机制（👍 / 👎）
- 没有 A/B 测试或 Prompt 效果追踪

#### 后果
- 系统优化方向缺乏数据支撑，只能依赖人工抽查
- 无法量化每次迭代（如新 Prompt、新模型）的真实效果
- 上线后的问题发现滞后，被动救火

---

### 3.8 核心服务过度耦合（God Class 问题）

#### 现状
`RAGService` 是一个**超 2000 行的大单体**，承担了：
- 意图识别
- 渠道推断
- 实体抽取
- 价格查询与数据分析
- 对话状态管理
- RAG 检索协调
- 向量库初始化与重建

#### 问题
- **职责边界模糊**：任何功能改动都可能影响其他模块
- **测试困难**：难以对单个能力写单元测试
- **扩展性差**：新增一个 Agent 能力需要继续往这个类里塞代码
- **协作瓶颈**：多人开发时极易产生代码冲突

---

### 3.9 Prompt 管理原始，工程化不足

#### 现状
所有 Prompt 集中在 `app/utils/prompt_template.py` 中，以**大段字符串常量**形式存在：

```python
Intent_TEMPLATE = """\
你是一个工程造价领域的智能助手...
"""
```

#### 问题
- 没有版本管理：改动 Prompt 没有历史记录
- 没有 A/B 测试：无法对比两个 Prompt 的效果
- 没有参数化验证：模板变量是否传齐，运行时才暴露
- 存在中英混杂：如 `RAG_template` 中英文夹杂，影响输出质量
- 没有 Prompt 优化框架：如 DSPy、LangChain Hub 等

---

### 3.10 配置安全与运行风险

#### 现状
```python
# app/config.py
DEEPSEEK_API_KEY = "sk-51657ec2e0854af19279f8826a322715"
```

#### 问题
- **API Key 硬编码**：泄露风险极高，且无法区分开发/测试/生产环境
- 没有环境变量隔离机制
- `dangerous_sql` 仅通过意图分类识别，没有输入层过滤（如 SQL 注入特征检测）
- 缺少输出审核（Output Moderation）
- 缺少速率限制（Rate Limiting）和并发熔断机制

---

### 3.11 前端不适合 Agent 交互模式

#### 现状
使用 Streamlit 构建单一页面，集成了：聊天、文件上传、文件删除、图表展示、状态轮询。

#### 问题
- 无法展示 **Agent 思考链（Chain of Thought）**：用户看不到"我在查什么、为什么这么查"
- 无法**中断或修正 Agent 执行**：一旦开始查询，用户只能等待结果
- 工具执行过程不可见：用户不知道当前是"在检索文档"还是"在调价格 API"
- 单页面耦合过重，不利于功能扩展

---

## 四、改进建议与升级路径

### 4.1 短期改进（1-2 个月，低风险）

#### 1. 修复全局对话历史
- 使用 `session_id` 隔离对话历史，存储在内存字典或 Redis 中
- 按 `session_id` 管理 `messages`，禁止全局变量

#### 2. 解耦 `RAGService`
- 将价格查询、对话管理、RAG 流程拆分为独立模块
- 每个模块提供清晰的接口，降低单文件复杂度

#### 3. 引入环境变量管理
- 将 API Key、数据库地址、模型地址迁移到 `.env` 文件
- 禁止在代码仓库中提交密钥

#### 4. 增加基础评估指标
- 记录每次检索的文档相关性得分
- 增加用户反馈按钮（👍/👎）收集数据
- 定期抽样检查 LLM 回答的幻觉率

---

### 4.2 中期升级（3-6 个月，架构调整）

#### 1. 引入标准 Tool Calling 框架
- 定义统一的 Tool Schema（如 OpenAI function calling 格式）
- 将价格查询、RAG 检索、计算器等封装为独立 Tool
- 让 LLM 根据用户问题自主选择调用哪些 Tool

#### 2. 构建 Agent Orchestrator
- 引入 **ReAct** 或 **Plan-and-Execute** 模式
- Agent 的核心循环：
  ```
  Thought → Action（调用 Tool）→ Observation → Thought → ... → Final Answer
  ```
- 支持多步任务和动态分支

#### 3. 升级 RAG 为 Agentic RAG
- 增加 **查询重写（Query Rewriting）** 模块
- 增加 **检索路由（Routing）**：区分法规、技术规范、价格数据
- 增加 **多跳检索（Multi-hop）** 支持
- 引入 **Self-RAG**：让 LLM 判断检索结果是否足够

#### 4. 增强记忆系统
- **短期记忆**：按会话维护上下文，支持多轮推理
- **长期记忆**：记录用户偏好、常用材料、历史查询
- **工作记忆**：保存 Agent 执行过程中的中间结论

---

### 4.3 长期演进（6-12 个月，产品化）

#### 1. 构建完整的 Agent 评估体系
- **检索评估**：Recall@K、MRR、NDCG
- **Agent 轨迹评估**：任务完成率、步数效率、工具选择准确率
- **答案质量评估**：Faithfulness、Relevance、Hallucination Rate
- **人工评估闭环**：A/B 测试、Prompt 版本对比

#### 2. 前端重构为 Agent 交互界面
- 展示 **思考链** 和 **工具执行过程**
- 支持用户**干预 Agent 执行**（如修改参数、重新选择工具）
- 支持**多模态输出**（表格、图表、引用文档高亮）

#### 3. 引入 Agent 框架
- 可考虑 **LangGraph**、**AutoGen** 或自研轻量框架
- 利用框架提供的状态管理、并行执行、人机协作（Human-in-the-loop）能力

## 六、总结

Easy-RAG 在**工程造价领域的 RAG 问答和价格查询**方面已经具备了可用的功能基础，工程实现上有不少亮点（如双缓冲向量库重建、流式响应、渐进式实体补全）。

但如果团队的目标是将其升级为真正的 **AI Agent**（能够自主规划、调用工具、反思修正、持续学习的智能体），则需要在以下四个核心维度进行结构性升级：

1. **推理与规划**：从 if-else 路由升级为 ReAct / Plan-and-Execute 循环
2. **工具抽象**：从硬编码函数升级为标准 Tool Registry + LLM 自主调用
3. **记忆系统**：从全局变量 + Slot Filling 升级为分层记忆（短期/长期/工作记忆）
4. **评估闭环**：从无评估升级为检索评估 + Agent 轨迹评估 + 用户反馈闭环

建议按照 **"先修隐患（P0）→ 解耦架构（P1）→ Agent 化升级（P2/P3）"** 的节奏稳步推进。
